# Deviations from `engineering_doc_v2.md`

Every place the implementation departs from, or adds to, the v2 engineering design. Each entry names the section it changes and why. Everything not listed here follows the document as written.

**1.1.0:** `docs/engineering_doc_v3.md` supersedes v2 for the sections listed in its §0 (setup window removed, resolution map, per-screen site deltas, two-line renameable screen card, Pause freezes). Entries that only described the setup window are marked **obsolete in 1.1.0** and kept for the 1.0.0 record; D21–D23 are the 1.1.0 deviations and cite v3 sections (plus the v2 section they replace); D24–D26 are the 1.1.0 **polish** pass from live use (one-click Restore, no `PIN` badge, size-only screen lines). Everything else still applies unchanged.

| D1 | **§5.5 `releaseZoom`** | `releaseZoom(tabId)` is `getZoomSettings` → return `'unchanged'` unless `scope === 'per-tab'` → `setZoom(tabId, defaultZoomFactor)` (if different, still in per-tab scope) → `setZoomSettings({mode:'automatic', scope:'per-origin'})`. The doc specifies only the final `setZoomSettings` call. | Verified in Chromium `components/zoom/zoom_controller.cc` (`SetZoomModeInternal`, `ZOOM_MODE_DEFAULT` branch): when a tab leaves isolated mode and the host has **no** stored per-origin level, Chromium calls `HostZoomMap::SetZoomLevelForHost(host, original_zoom_level)` — i.e. it would copy AutoZoom's 125% into Chrome's per-site memory, breaking §0 decision 3 ("Chrome's own zoom memory is never written"). `HostZoomMapImpl::SetZoomLevelForHostInternal` erases entries equal to the default, so resetting the tab to `defaultZoomFactor` first makes that copy a no-op. If the host *does* have a stored level Chromium restores it and the reset is harmless. The interim `setZoom` runs in per-tab scope so it cannot leak to sibling tabs, and every release path writes its storage guard (`enabled=false` / `excludedHosts[host]=true`) **before** releasing, so the stateless detector ignores the resulting event. `chrome.tabs.setZoom(` therefore appears twice in `tab-zoom.js`, both times with per-tab scope already established. Covered by the test *"releaseZoom restores a pre-existing Chrome per-origin level and never persists AutoZoom's value"*. |
| D2 | **§5.7 `handleZoomChange`** | Added a second early-return: `if (isSameZoom(oldZoomFactor, newZoomFactor)) return;` between the scope guard and the storage read. | Verified in `zoom_controller.cc`: switching a tab to isolated (per-tab) mode calls `SetTemporaryZoomLevel(rfh, original_zoom_level)`, which dispatches `tabs.onZoomChange` with `scope: 'per-tab'` and `old === new === current zoom` **before** AutoZoom's own `setZoom`. Under the doc's algorithm that echo (e.g. 1.0 on a 125% screen) differs from `expected` and would be recorded as a spurious −2 delta — and because the handler for the echo can finish after the handler for the real `setZoom` event, the bad delta could persist. A genuine `Cmd +/−/0` always changes the factor, so `old === new` carries no user intent. Still stateless; no TTL lock. `_chrome-mock.js` reproduces the echo and scenario 1 asserts `siteStepDeltas` stays empty. |
| D3 | **§5.6 `targetFor`** | Returns `null` also when `!state.onboardingCompleted`. **Still true in 1.1.0** — the confirm is now the toolbar popup's first-run **Accept** (`CONFIRM_SETUP`, v3 §7) instead of the setup window. | §6 says "Do **not** zoom anything until the user confirms" for first install; making it a property of `targetFor` guarantees it for every path (focus events, tab activation) rather than only `onInstalled`. In 1.1.0 the same gate also covers the no-prompt immediate apply for new screens (nothing is applied anywhere before Accept), the first-run popup being closed without Accept, and the `update` path for a v2 user who never finished setup (first-run popup again, nothing zoomed until Accept). The engine tests set `onboardingCompleted: true` in their fixture. |

| D6 | **§7 Setup window** — **obsolete in 1.1.0** | **Obsolete in 1.1.0:** the setup window is removed (v3 §0). A screen discovered after first run is applied immediately at its recommended zoom with no prompt to dismiss, and first run is the popup's own state — closing the popup without Accept changes nothing and the same state shows on the next click, so there is no *Finish setup* banner or `OPEN_ONBOARDING` either. 1.0.0 behaviour: closing the **new-display** prompt without clicking Apply marks the pending screen(s) `confirmed: true` at their default (125%) and clears `pendingSetupKeys`. | The doc specifies the dedupe but not what happens on dismiss; without this, every focus change would re-open the prompt. The onboarding window is **not** auto-confirmed on close: `onboardingCompleted` stays `false`, nothing is zoomed (D3) and the popup shows a *Finish setup* banner with an `OPEN_ONBOARDING` message. |

| D21 | **v2 §8 Global toggle off / v3 §5.4 `setEnabled`** (1.1.0) | **Pause freezes instead of releasing.** `SET_ENABLED false` only writes `enabled=false` and sets the `OFF` badge on active tabs — no `releaseAll()`, zero `setZoom` / `setZoomSettings` calls. Tabs stay in per-tab scope at whatever zoom they have; Chrome itself returns each tab to per-origin on its next cross-document navigation. **While paused, a `Cmd +`/`Cmd −` on a frozen tab is per-tab only**: it is not recorded by AutoZoom (the `enabled=false` guard in `handleZoomChange`), is not remembered by Chrome per origin, and is discarded on that tab's next navigation. **Resume** (`SET_ENABLED true`) re-applies AutoZoom's screen defaults and site steps to every tab on every connected screen (`resyncAllWindows` + `normalizeScreen` per connected key), overwriting any such per-tab change. `RELEASE_ALL` ("Restore Chrome's zoom") is wired to `patchState({enabled:false})` + `releaseAll()` and is now the **only** release path besides Exclude and uninstall. | Product decision 4.1–4.4 in `docs/change_proposals_review.md`: pausing should not visibly re-zoom every tab; the user who wants Chrome's zoom back has an explicit action for it. v2 §8 had toggle-off = `releaseAll()` and PRD FR-13 / Journey 6 said the same — both amended for 1.1.0, as is the "Not deviations" bullet below. Users should not expect Chrome-native zoom while paused (pitfall B4): the popup label is just *Paused*. Specified regression scenarios (v3 §10): *Turn Off: zero `setZoomSettings`/`setZoom` calls, tabs keep zoom* · *Resume: every tab on every screen re-applied*; plus, per pitfall A2, `RELEASE_ALL` must still issue ≥ 1 per-origin `setZoomSettings`. |
| D22 | **v2 §5.7 `handleZoomChange` ("0 ⇒ removes the entry") / v3 §5.2 `site-deltas.js`** (1.1.0) | **Explicit `0` delta rows block inheritance; a host whose rows are all `0` is pruned.** A user `Cmd ±` writes `siteStepDeltas[host][screenKey] = { delta, updatedAt }` for the **current** screen even when `delta` is `0`. `resolveDelta` returns an explicit row before considering inheritance (same class → smallest \|Δ logical area\| → most recent `updatedAt`), so a `0` row means "this screen's default, do not inherit". `withDelta` deletes the host only when **every** row is `0`; `setExcluded(host, true)` clears all rows for the host; the former `CLEAR_SITE_DELTA` / "Reset site" button is removed. | Without a persisted `0` the Gmail scenario breaks: `+1` on the external, `Cmd −` back on the built-in screen, next sync re-inherits the external's `+1`. Pruning all-`0` hosts keeps the popup's "Clear all site exceptions" count meaningful. Consequence (pitfall B2): once a screen has an explicit `0` for a host it never inherits for that host again; the ways back are *Clear all site exceptions* or exclude → re-include the site. Covered by the v3 §10 `site-deltas.test.js` scenarios *explicit 0 blocks inheritance* and *host with all-0 rows is pruned*, and the `zoom-engine.test.js` Gmail scenario. |
| D23 | **v3 §6 `runtime.onInstalled` `install` → `chrome.action.openPopup()`** (1.1.0) | **First-run popup open failure: logged, retried once on the next window focus, then waits for an icon click.** If `openPopup()` rejects at install (or on `update` with `onboardingCompleted=false`), the error is logged and AutoZoom retries the call **once** on the next `windows.onFocusChanged` while first run is still unaccepted; after that it is silent until the user clicks the toolbar icon, which shows the same first-run state. Nothing is zoomed in the meantime (D3). | v3 §6 says the failure is "logged and ignored". Realistic failure modes (pitfall B1): Chrome's own "extension added" bubble is open at the moment `onInstalled` fires (the common path), no focused normal window (sync/policy install, Chrome in background), or a popup already open. With the `!` badge out of scope and the icon unpinned behind the puzzle menu, a silent first failure would leave AutoZoom dormant with zero UI; one retry on the next focus change recovers the common case without adding a window or a badge. Specified scenario (v3 §10): *install → `chrome.action.openPopup` called once; rejection swallowed*, plus the focus-change retry. |

## Not deviations (worth stating)

- **`setTimeout` for the 150 ms / 500 ms / 1500 ms timers** — as the doc's §6 note prescribes (`chrome.alarms` minimum is 30 s).
- **`Cmd+0`** is recorded as a normal delta (R5 / §9 "pending decision" resolved as "honor it").
- **Screen defaults are absolute ladder values**; Chrome's *Page zoom* setting is ignored (R5).
- **Pause releases immediately; Resume re-applies to active tabs** (R5), background tabs are re-managed lazily on activation (FR-8). *(1.0.0 only — superseded in 1.1.0 by D21: Pause freezes, Resume re-applies to every tab on every connected screen.)*
- **Live-Chrome smoke test**: the builder could not obtain the `chrome-devtools-mcp` permission in this session, so behavioural criteria were verified by a static audit plus `tests/service-worker.test.js`, which boots the real `service-worker.js` against the mock and drives install → onboarding → confirm → Cmd ± → navigation → drag → minimize → display change → pause/resume.

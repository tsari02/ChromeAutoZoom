# Deviations from `engineering_doc_v2.md`

Every place the implementation departs from, or adds to, the v2 engineering design. Each entry names the section it changes and why. Everything not listed here follows the document as written.

| # | Doc section | Deviation | Reason |
|---|-------------|-----------|--------|
| D1 | **§5.5 `releaseZoom`** | `releaseZoom(tabId)` is `getZoomSettings` → return `'unchanged'` unless `scope === 'per-tab'` → `setZoom(tabId, defaultZoomFactor)` (if different, still in per-tab scope) → `setZoomSettings({mode:'automatic', scope:'per-origin'})`. The doc specifies only the final `setZoomSettings` call. | Verified in Chromium `components/zoom/zoom_controller.cc` (`SetZoomModeInternal`, `ZOOM_MODE_DEFAULT` branch): when a tab leaves isolated mode and the host has **no** stored per-origin level, Chromium calls `HostZoomMap::SetZoomLevelForHost(host, original_zoom_level)` — i.e. it would copy AutoZoom's 125% into Chrome's per-site memory, breaking §0 decision 3 ("Chrome's own zoom memory is never written"). `HostZoomMapImpl::SetZoomLevelForHostInternal` erases entries equal to the default, so resetting the tab to `defaultZoomFactor` first makes that copy a no-op. If the host *does* have a stored level Chromium restores it and the reset is harmless. The interim `setZoom` runs in per-tab scope so it cannot leak to sibling tabs, and every release path writes its storage guard (`enabled=false` / `excludedHosts[host]=true`) **before** releasing, so the stateless detector ignores the resulting event. `chrome.tabs.setZoom(` therefore appears twice in `tab-zoom.js`, both times with per-tab scope already established. Covered by the test *"releaseZoom restores a pre-existing Chrome per-origin level and never persists AutoZoom's value"*. |
| D2 | **§5.7 `handleZoomChange`** | Added a second early-return: `if (isSameZoom(oldZoomFactor, newZoomFactor)) return;` between the scope guard and the storage read. | Verified in `zoom_controller.cc`: switching a tab to isolated (per-tab) mode calls `SetTemporaryZoomLevel(rfh, original_zoom_level)`, which dispatches `tabs.onZoomChange` with `scope: 'per-tab'` and `old === new === current zoom` **before** AutoZoom's own `setZoom`. Under the doc's algorithm that echo (e.g. 1.0 on a 125% screen) differs from `expected` and would be recorded as a spurious −2 delta — and because the handler for the echo can finish after the handler for the real `setZoom` event, the bad delta could persist. A genuine `Cmd +/−/0` always changes the factor, so `old === new` carries no user intent. Still stateless; no TTL lock. `_chrome-mock.js` reproduces the echo and scenario 1 asserts `siteStepDeltas` stays empty. |
| D3 | **§5.6 `targetFor`** | Returns `null` also when `!state.onboardingCompleted`. | §6 says "Do **not** zoom anything until the user confirms" for first install; making it a property of `targetFor` guarantees it for every path (focus events, tab activation) rather than only `onInstalled`. The engine tests set `onboardingCompleted: true` in their fixture. |
| D4 | **§1 Files** | Added `src/lib/setup-window.js` (setup-window launcher/dedupe) and `scripts/static-scan.mjs`; added `tests/index.js`, `tests/storage.test.js`, `tests/sync-scheduler.test.js`, `tests/badge.test.js`, `tests/message-router.test.js`, `tests/service-worker.test.js`; added a dependency-free `package.json`. | `setup-window.js` keeps `zoom-engine.js` focused on zoom (the doc's §7 logic had no named home). `static-scan.mjs` automates the acceptance-criteria static scan. `tests/index.js` exists because Node's test runner treats the literal argument `tests/` as a module path, not a directory; the index imports every `*.test.js` so `node --test tests/` runs the whole suite (and `node --test` with no args still discovers the files individually). `package.json` only sets `"type": "module"` and convenience scripts — zero dependencies. |
| D5 | **§5.2 `matchSavedScreen`** | Pure: returns `{ key, screen, needsIdUpdate }` and never mutates; the caller (`zoom-engine.js`) persists `lastSeenDisplayId`. | The doc says the function "updates `lastSeenDisplayId` on match", but it is listed under the PURE modules; mutating the saved record inside a pure helper would make the unit tests order-dependent. Behaviour is identical. |
| D6 | **§7 Setup window** | Closing the **new-display** prompt without clicking Apply marks the pending screen(s) `confirmed: true` at their default (125%) and clears `pendingSetupKeys`. | The doc specifies the dedupe but not what happens on dismiss; without this, every focus change would re-open the prompt. The onboarding window is **not** auto-confirmed on close: `onboardingCompleted` stays `false`, nothing is zoomed (D3) and the popup shows a *Finish setup* banner with an `OPEN_ONBOARDING` message. |
| D7 | **§8 Popup message table** | `SET_SCREEN_ZOOM` writes storage, responds immediately, then runs `normalizeScreen` in the background (`setScreenZoom(key, factor, { awaitNormalize })`). Added `GET_POPUP_STATE`, `GET_SETUP_DATA`, `OPEN_ONBOARDING` messages, and a `__external_default__` pseudo-row key for the "External monitors you plug in later" onboarding row that maps to `defaults.external`. | §5.6 requires `normalizeScreen` to "not block UI responses"; §7 lists `CONFIRM` but no read messages, so the data contracts had to be defined. All handlers keep the async-IIFE + `return true` pattern. |
| D8 | **§6 `tabs.onUpdated`** | Also triggers `syncTab` on `changeInfo.discarded === false`, and `tabs.onRemoved` is a no-op. | Un-discarding is the case the doc calls out; the explicit flag is the cheapest signal. Badge text is tab-scoped and dies with the tab, and `windowScreen` is keyed by window, so `tabs.onRemoved` has nothing to clean. |
| D9 | **§5.6 `normalizeScreen` return value** | Returns `{ updated, applied, unchanged, skipped }` (superset of the doc's `{ updated, skipped }`). | Lets scenario 6 assert the exact `applyZoom` count (110) separately from unchanged tabs. |
| D10 | **§4 storage.session writes** | Read-modify-write of `windowScreen` / `pendingSetupKeys` / `setupWindowId` is serialized through an in-process queue in `storage.js`. *(Fix round 1: the same queue now covers `storage.local` too — see D15.)* | Concurrent `syncWindow` calls during a display-change burst would otherwise lose updates to the shared `windowScreen` map. The queue is a cache-like in-memory structure (losing it on SW restart costs nothing). |
| D11 | **§5.5 `isManageable`** / **FR-9** | `isZoomableUrl` is an allow-list (`http:`, `https:`, `file:`) that additionally rejects `chrome.google.com` and `chromewebstore.google.com`; `hostOf('file:…')` returns the pseudo-host `"file"`. | Matches what `chrome.tabs.setZoom` actually permits and keeps `file:` pages from sharing a `''` host key. |
| D12 | **§2 Manifest** | Added `"default_title": "AutoZoom"` to `action`. | Cosmetic; `badge.js` overrides the title per tab. |
| D13 | **UI styling** | Light/dark theming uses `prefers-color-scheme` media queries with CSS custom properties rather than `light-dark()`. | `light-dark()` requires Chrome 123; the manifest's `minimum_chrome_version` is 102. `color-scheme: light dark` is still declared so native controls adapt. |
| D14 | **§7 Setup window dedupe** (fix round 1) | `openOnboarding` / `requestNewDisplayPrompt` run inside a module-level single-flight lock (`withOpenLock`) in `setup-window.js`; the persisted `setupWindowId` remains the cross-restart dedupe. | The doc's read → create → write dedupe is not atomic: `resyncAllWindows` runs `syncWindow` for N windows concurrently and each could open a prompt for the same unconfirmed display (auditor reproduced N windows). The lock is a cache (restart-safe thanks to the stored id). Regression test: *"N windows on one unconfirmed display + resyncAllWindows → exactly one prompt window"*. |
| D15 | **§4 storage writes** (fix round 1; supersedes D10) | **Every** read-modify-write of `storage.local` (`setSiteStepDelta`, `setExcludedHost`, `upsertScreen`, `updateScreens`, `confirmSetup`, `syncDisplays`, `patchState`, `initState`, `migrate`) and of `storage.session` goes through one in-process `serialized()` queue in `storage.js`; new `updateState(fn)` / `updateScreens(fn)` helpers recompute from the current value inside the queue. | Two concurrent `setSiteStepDelta` calls lost one write; `resyncAllWindows` upserting `lastSeenDisplayId` concurrently with the popup's `SET_SCREEN_ZOOM` could revert the user's choice. Regression test: *"concurrent storage.local read-modify-writes never lose an update"*. |
| D16 | **§7 Onboarding placement** (fix round 1) | The onboarding window opens on the display under the last-focused *normal* window (`chrome.windows.getLastFocused({windowTypes:['normal']})` → `resolveDisplay`), falling back to the primary display. The new-display prompt still opens on that display when connected, else where the user is looking. | Live run: the user had Chrome on the external display, the prompt opened on the (primary) built-in screen and went unnoticed. Tests: *"OPEN_ONBOARDING … on the display of the last-focused normal window"* and *"… falls back to the primary display"*. |
| D17 | **§5.2 Screen keys for nameless displays** (fix round 1) | `slug('')` is now `''`; `externalKeyBase(display)` returns `ext:<slug>` when a name exists, else `ext:<w>x<h>` from the DIP bounds. `displayLabel` labels nameless externals "External Display · 2560×1440". `#2/#3` suffixes still order identical bases by ascending id. | Live run: macOS Chrome returned `name: ""` for both displays, so every nameless monitor collapsed into `ext:external`. Resolution is used **only** in the nameless fallback, so §5.2's "resolution is not part of the key" still holds for named displays. Documented limitation (README): identical monitors may swap profiles if macOS re-numbers ids. A profile saved under the old `ext:external` key by a pre-fix build is not migrated (one extra new-display prompt). |
| D18 | **§5.5 `applyZoom` / `releaseZoom`** (fix round 1) | Per-tab single-flight (`perTab` map in `tab-zoom.js`): overlapping operations on the same tab run sequentially, so the second sees the first's result and becomes `'unchanged'`. Different tabs are not serialized (pool concurrency and scenario 6's exact-110 count unaffected). | Live run: after onboarding confirm the active tab received `setZoom(1.25)` twice within 5 ms (`normalizeScreen` and the focus-change `syncWindow` overlapped). Harmless but wasteful. Regression test: *"overlapping applyZoom on the same tab issues a single setZoom"*. |
| D19 | **§8 `SET_SCREEN_ZOOM`** (fix round 1) | `setScreenZoom` throws `Unknown screen key` for keys with no saved profile; `GET_POPUP_STATE` sorting tolerates profiles without a `name`. | A nameless profile created through an arbitrary key crashed `a.name.localeCompare` in the popup state builder. Tests in `zoom-engine.test.js` and `message-router.test.js`. |
| D20 | **Packaging** (fix round 1) | `scripts/package-extension.sh` also emits `dist/unpacked/` and README instructs loading that folder. | Chrome refuses to load the repository root unpacked: `_agents/` starts with `_`, which is reserved (`_locales`). The agent folders must not be touched, so the loadable copy lives in `dist/`. |

## Not deviations (worth stating)

- **`setTimeout` for the 150 ms / 500 ms / 1500 ms timers** — as the doc's §6 note prescribes (`chrome.alarms` minimum is 30 s).
- **`Cmd+0`** is recorded as a normal delta (R5 / §9 "pending decision" resolved as "honor it").
- **Screen defaults are absolute ladder values**; Chrome's *Page zoom* setting is ignored (R5).
- **Pause releases immediately; Resume re-applies to active tabs** (R5), background tabs are re-managed lazily on activation (FR-8).
- **Live-Chrome smoke test**: the builder could not obtain the `chrome-devtools-mcp` permission in this session, so behavioural criteria were verified by a static audit plus `tests/service-worker.test.js`, which boots the real `service-worker.js` against the mock and drives install → onboarding → confirm → Cmd ± → navigation → drag → minimize → display change → pause/resume.
